## 1. 选型与内存预算

推荐方案：数据库保存权威配置，进程内缓存有容量限制的不可变快照。文件不作为动态配置缓存；当前不新增同机 Redis。

- [ ] 测量空闲、典型收发、大附件和高并发时的 RSS、托管堆、GC 与内存峰值；确认服务器总内存、其他服务和进程数量后确定预算，记录 cgroup／systemd 内存限制与 OOM 事件。
- [ ] 提供缓存总预算、单快照大小、缓存域数量、TTL、逐出策略和禁用开关。可先评估整台服务器配置缓存 4–8 MiB 的保守起点；这不是实测值或进程内存上限承诺。多进程须拆分总预算，不能各自使用整台预算。
- [ ] 按活跃域懒加载，不全域预热；计入字符串、数组、字典、匹配对象等开销。序列化字节数不等于实际内存，应用预算不能保证整个进程不会 OOM，需用 RSS／堆指标校准。
- [ ] 超预算时采用有界数据库查询；禁止先加载全量再决定不缓存。大型规则分批评估须保持优先级与同版本语义；大型防火墙配置需设计有界回退或准入限制。
- [ ] 限制并发加载及重载规模，合并同键加载；测量新旧快照同时存活的峰值。逐出后处理中的邮件可能仍引用旧快照，不能假设立即释放内存。
- [ ] 对缓存锁、加载任务、负结果和版本字典也设生命周期与上限，防止辅助结构持续增长。检查现有账号级静态锁表的安全清理方式，保证互斥正确。
- [ ] 小内存单机优先评估 `run all` 共用配置快照，减少多个进程的重复占用；保留拆分进程能力，说明两者故障隔离差异。

## 2. P1：规则、防火墙与设置快照

- [ ] 收发信规则按域 ID＋方向缓存，预解析条件 JSON、通配符模式和动作，保持规则及动作顺序；同一邮件处理固定规则版本。当前 `MailRuleService.MatchAsync` 与 `EvaluateOutgoingRejectionAsync` 会重复加载规则图。
- [ ] 防火墙缓存已解析 IPv4／IPv6 网段，避免每连接读取全部启用规则并重复解析 CIDR；定义规则变更对新连接和已有连接的生效语义。
- [ ] 缓存 SMTP、投递、全局／域邮箱默认设置，减少 SMTP 每连接、Worker 每轮及完成投递时的查询；明确各类设置生效时点。Singleton 服务不等于已缓存数据。
- [ ] 第二阶段评估账号／别名规范化地址到账号 ID 的路由映射；账号停用、删除、域停用、别名转移必须及时失效。无规则／无别名等负结果短期缓存，新建后及时失效。
- [ ] 仅缓存不可变视图，不缓存 DbContext 或跟踪实体；密码、权限撤销、配额、投递租约与状态、IMAP UID／ModSeq／标志保持数据库权威。
- [ ] 邮件正文、附件、完整 MIME 和整箱 IMAP 结果不进入配置常驻缓存；避免把预编译通配符做成无界全局缓存。

## 3. P1：持久化、跨进程失效与故障处理

- [ ] 增加作用域配置版本，配置更新与版本递增同事务提交；提交成功才更新或失效本地快照。覆盖 API、CLI、维护任务等所有写入路径，直接改数据库需定期重载兜底。
- [ ] 多进程批量轮询配置版本并原子替换快照；初始评估 2–5 秒检查周期，测量后确定。明确保存到全部进程生效的延迟上限，安全决策要求立即生效时另设同步确认或决策时版本检查。
- [ ] 重载失败不发布半成品，保留旧快照并告警；首次加载、版本检查失败及数据库中断需明确策略，防火墙与拒绝发信规则不能静默退回允许。必要时暂拒／延迟处理。
- [ ] 显示保存版本、运行版本与生效情况；记录命中、未命中、加载耗时、快照年龄、大小、失效延迟和重载失败指标。

## 4. P1／P2：缓存之外的修复

- [ ] P1：Direct MX 长时间多 MX／IP 尝试期间续租；完成任务时核对租约所有者和版本，故障注入验证多 Worker 不重复投递。租约与状态继续使用数据库原子写入。
- [ ] P1：隔离 Worker 动态设置读取与完成投递的异常，防止单轮错误终止整个服务循环。
- [ ] P1：隔离 SMTP／IMAP 单连接防火墙或数据库故障，保留监听循环，按明确策略拒绝连接并上报健康状态。
- [ ] P2：IMAP SEARCH／FETCH／列表查询推到数据库，检查索引，按需读取 MIME，避免整箱加载；对确需扫描正文的搜索采用有界批次。
- [ ] P2：邮件输入、大附件解析与 FETCH 尽量流式／分块；限制 SMTP／IMAP 连接、投递并发、后台批次和缓冲区，预留操作系统及 API 内存。缓存限额无法限制这些内存来源。
- [ ] P2：存储完整性扫描增加可续扫游标和进度，避免反复扫描同一批前序记录，记录覆盖率与失败重试。
- [ ] P2：补 SMTP／IMAP／Worker 独立进程心跳及健康快照，与原清单 BE-01／BE-02 合并实施，API readiness 不代表所有进程正常。

## 6. 内存、Redis、文件的使用范围

| 方案 | 当前选择 | 用途和边界 |
| --- | --- | --- |
| 有界进程内缓存 | 首选 | 规则、防火墙、少量设置；数据库为权威，按需加载，版本失效，重启重建 |
| Redis | 当前不引入 | 同机 Redis 仍占服务器内存并增加运行开销；未来多主机或有实测共享缓存需求时再评估，使用通知／短 TTL，版本轮询兜底 |
| 文件缓存 | 不用于动态规则 | 适合静态资源、证书及可重建离线产物；动态规则的原子更新、跨进程同步和失效更复杂，且文件读取解析仍占内存 |

远端 Redis 也不能解决本地邮件解析、反序列化和并发缓冲的峰值；Redis 的内存限制也不代表整台服务器或整个进程的硬上限。现有 DNS 检查结果继续使用数据库持久化与手动刷新，无需再建文件副本。
