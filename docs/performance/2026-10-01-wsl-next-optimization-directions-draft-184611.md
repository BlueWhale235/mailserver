# 下一轮综合优化方向（源码与现有证据草稿）

这里区分已测瓶颈与源码候选；未有 runtime/SQL 证据的事项不会写成确定性能收益。最终 protocol-final 数据与独立诊断完成后再调整排序。

|优先级|方向|当前依据|下一步最小实验|约束|
|---|---|---|---|---|
|P1|缩小后台清理/配额校准锁范围|MaintenanceTaskServices 的 Reconcile/PurgeOne 当前先枚举并锁全部域；一次单对象清理可能阻塞其他域写入。属于源码推断，未有前台等待实测|同一压力下触发一个测试域清理，比较其他域收信 P95 与 MySQL 锁等待；先确定全部目标域，按 ID 顺序只锁目标|保持 Serializable、配额一致性和固定顺序，目标变化重建，不能事务中逆序补锁|
|P1|后台游标查询与到期失败查询索引|检索表目前只有 MessageId 主键；到期查询过滤 ParserVersion/Status/RetryAfter 后排序 ReceivedAt/Id，潜在扫描成本。旧空闲轮询已经 30 秒|使用已有 EXPLAIN/rows_examined 和 100k 尾部 backlog 对照；只有扫描证据支持时加复合索引|MySQL ReceivedAt 二级索引已隐含主键，不盲加重复 (ReceivedAt,Id)；SQLite 单独验证计划|
|P1|补建持久化次数|每封记录读取/保存，然后游标再次读取/保存；即使选择已用游标，16 封仍有多次 durable DB 写入|单进程先将记录与游标同事务持久化，比较每封 SQL/提交与崩溃续作；再验证多进程竞争|游标与记录必须原子，失败可重试，不能越过未处理记录造成遗漏|
|P2|大邮箱检索批次固定成本|32 封每批一次索引查询已满足要求，但 100k 独立正文仍需约 3125 批，临时快照及往返成本持续存在|依据大邮箱 SQL、分配与 trace 确认数据库/临时文件占比；测有界批次内部复用缓冲和共享 MessageId 重用|仍每批≤32，保持 Unicode 子串语义，不用数据库不同 collation 或分词搜索偷换协议；禁止整箱无界缓存|
|P2|暂存移交小邮件开关收益|10 MiB 五轮 P95 均改善；1 MiB 聚合门槛未达标且主要单轮异常，不能说稳定退化|在最终产物同配置重复 off/on，记录 per-round 磁盘/CPU/GC；准备路径默认关闭直至获得一致收益|同设备校验、所有权清理、哈希校验与跨设备安全复制不能删|
|P2|复杂大 MIME 回退分配|ASCII 原文回退已分块，复杂 Unicode/编码/附件沿既有完整路径；当前是保语义选择|独立 trace 看具体 TextPart 解码和归一化分配，选真实占用大的单一路径做有界解码实验|跨块 Unicode 大小写与编码解码须与既有子串结果严格一致；不能因索引截断漏结果|
|P3|收信额度与重操作等待成本|最终容量 c2/c4 全接受；c8/c16 有明显 451，活跃保护保持 4；并发提高不能等同优化|用许可等待/入站文件保存/DB 事务分段证据判断先做等待唤醒、锁或存储；保持任务 4/重 MIME 2 比较|不按照 16 GiB 自动放大任务到几十；没有真正 1 GiB 验收不改变小内存默认|

已确认值得保留的方向是减少持久 IMAP 小响应等待、按需字段投影与紧凑快照、安全 ASCII 分块匹配、选择范围下推以及固定顺序配额锁。其精确归因仍要结合最终默认配置对照，不能将组合收益全算到单个优化。

原生工具应先看 CPU 样本、分配类型、GC 暂停与数据库等待，再决定新优化。Speedscope/PerfView 等 thread-time 栈含等待时不能当纯 CPU 热点；采集窗口吞吐不能与无采集窗口直接混比。文件缓存增加也不能据此判断托管内存泄漏。

旧 887 MiB 云端、Azure MySQL、Windows 客户端与当前大内存本地 MySQL/回环客户端差异很大，只能讨论容量和环境限制，不能计算代码收益。当前最终持续负载是各 10 分钟，不替代真正整机 1 GiB 或长期运行验收。

## 新增正式证据调整优先级

P1：共享 10k 的 UNSEEN 五轮可重复退化（P95 +26.72%、吞吐 -23.41%），优先定位快照/传输/Flags 处理。P1：2 万条种子 COPY 超时需根因诊断，2k 跟踪预算及回滚测试已通过，不能据超时直接说跟踪膨胀。P2：single UID COPY 内容实体返回已经 10000→2，但 MAX(Uid) digest examined 10000，继续研究有序端点/过滤计划和避免无需最大值的 UID 选择，保持 UID 星号与软删除语义。
