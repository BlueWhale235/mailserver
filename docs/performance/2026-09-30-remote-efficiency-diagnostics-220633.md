# 远端部署、资源档位压测与诊断 API 分析

2026-09-30，在 `20.24.67.236` 的 `/www/mailserver` 部署当前工作区版本，使用 Azure MySQL `app-mailserver`。管理入口为 `https://20.24.67.236:5000/admin/`，使用测试部署的自签名证书。按用户要求清空旧应用数据及目标 MySQL 中的全部表，未创建备份；重新初始化管理员、测试域、测试邮箱和证书。新的访问凭据只保存在被 Git 忽略的 `builds/private/remote-admin-credentials.json`，不写入报告。

## 环境与比较范围

实际服务器为 2 vCPU，内存 **930,234,368 B，约 887 MiB**，Swap 2 GiB。这里的 `1gb` 和 `32gb` 是应用资源配置档位，**不是两台不同内存容量的机器**。负载从独立 Windows 客户端，经公网 SMTP 25 端口进入；服务所有角色与 MySQL 客户端都运行在同一进程中。

本轮优化前二进制 SHA256：`68aece876a7865c4ac3f1c667cdb2d82201e4c64620a7a8112969bc817b7ddd1`。优化后二进制 SHA256：`0e180eefccb55960790d3cbdfb971c51621747b1998b2bca6fe0589139c64dcb`。两版均来自实施开始时的完整工作区及后续效率实现，**此处的“优化前”指远端发现超大检索文本内存问题之前的版本，不是最初未实现五阶段计划的代码**。最初版本的查询微基准另见 [效率实现报告](2026-09-30-efficiency-optimization.md)。

压测临时放宽 SMTP 入站和 IMAP 的来源保护：每分钟 10000、突发 2000、来源并发 2000；应用内存资源上限继续生效。`1gb` 档实际 SMTP 连接上限 16、IMAP 32、活跃邮件 2、投递任务 2、缓存预算 8 MiB；`32gb` 档实际 SMTP 1774、IMAP 1024、活跃邮件 3、投递任务 64、缓存预算 256 MiB。测试邮箱配额临时提高到 8 GiB，以容纳测试积累。

固定 1/10 MiB ASCII 邮件，每种大小预热一次；每轮双并发发送 4 封，三并发发送 6 封，每种组合最多五轮，轮间休息 3 秒。过程中的停止阈值：服务进程 Swap 超过 128 MiB、宿主可用内存低于 150 MiB、健康检查失败或发送错误。前后测量是顺序进行，未完成五轮交替版本测量；邮箱数据随测试增长，公网流量也有明显波动，因此不能作为严格的无退化证明。

## 诊断 API 与实际优化

测试通过管理员令牌启用 `/api/v1/operations/performance/diagnostic`，获取 `summary?kind=operation|stage|sql`、操作列表及详细阶段。诊断模式最多持续 15 分钟，短测期间详细采样为 100%；持续测试到期后恢复常规采样。排名使用分钟聚合，区间起点不在整分钟时会遗漏第一段分钟数据，P95 来自直方图，是近似值；嵌套阶段总时间不能相加当作端到端耗时。

发现并修复的两个具体问题：

1. 超大正文补建检索数据时，原实现先完整解码、规范化正文，再截断为 512 KiB，造成大量瞬时分配和 Swap。现在先检查可定位文本部分的长度，超限时保存规范化邮件头，将正文记录标记为不完整；搜索继续回退原文，保持结果，不强行构造全部检索文本。增加了超大正文回归，并为后台处理加入 `search.backfill`、`search.mime-parse`、`search.normalize` 阶段诊断。
2. SQL 排名及操作明细 API 在 Azure MySQL 上会返回 500，原因是提供程序无法映射 `fingerprints.Contains(...)` 的集合参数。改用有界等值参数查询。优化后两档 SQL 排名和各 12 份详细操作均成功导出。

## 持续负载与最终状态

最终优化二进制、远端 MySQL、1gb 档，交替 1/10 MiB、2/3 个请求，轮间目标 10 秒，运行 **1800 秒、175 轮**。成功收信 **367 封、2,064,630,594 B（约 1.92 GiB）**，非限流错误 **0**，明确的 **451 资源限流 70 次**，健康检查 **175/175 成功**。成功请求整体 P95 **5.594 秒**。这是稳态可靠性测试，不是极限吞吐测试，也不是外发 Direct MX 压测。

1811 个内存样本覆盖运行及收尾采集，进程 RSS 采样峰值 **295.5 MiB**，内核记录历史峰值 **301.6 MiB**，结束附近 RSS **212.5 MiB**；进程 Swap 采样峰值 **41.9 MiB**，宿主最小可用内存 **312.5 MiB**。没有触及停止阈值，但不能称为零 Swap。补充 CPU 采样覆盖后约 25 分钟，平均 **5.46% 单核**、一秒样本最大 **45.97% 单核**，不是总机 CPU 百分比。RSS 未持续增长，但单次 30 分钟运行不足以证明不存在慢速泄漏。

进程级 GC 日志首尾样本的累计分配增加 **4,083,188,344 B（约 3.80 GiB）**，Gen0/1/2 计数分别增加 **300/255/63**；末尾 GC 堆约 **71.7 MiB**。这些数据包含所有服务角色、后台补建和诊断采集，不能归属到单封邮件或单个方法；下一轮的分配 trace 用于定位其来源。

进程最后一次 I/O 样本累计 `write_bytes=4,141,056,000`（约 3.86 GiB），`read_bytes=784,855,040`。I/O 样本在启动后约四分钟开始，不能把整个累计量都当作该采样区间增量；后约 25 分钟的写入增量为 3,541,733,376 B。源码中 SMTP DATA 先写临时文件，`FileMessageContentStore.SaveAsync` 再复制到内容库；累计写入约为接收正文的两倍，与这条路径相符，但还包含日志等其他写入，不是逐条文件写入归因。

## 后续改进优先级

1. **搜索的部分数据状态细化。** 当前超大正文省略后整条记录为 `Incomplete`；即使邮件头已完整保存，邮件头条件不匹配时也会保守回退原文。应区分邮件头完整性与正文完整性，使邮件头查询可直接判定，正文查询继续安全回退。正文回退路径仍会解码和规范化完整文本，需要用有界或流式实现保留现有 Unicode/子串语义，并实测正向与无匹配查询。
2. **减少接收邮件的重复落盘。** 评估受控临时文件所有权移交、边接收边计算内容哈希、同文件系统完成文件的原子接管；跨文件系统保留复制回退。必须保留配额、持久化时序、原始内容完整性及失败清理，不能简单删掉第一份临时文件。本轮未实现该改动。
3. **IMAP 收取和大邮箱状态路径。** 分开记录连接/TLS/登录、SELECT、STATUS、FETCH 和网络发送；补充持久连接的 FETCH 对照，避免把每封重新连接的成本误判为读取成本。本轮小邮箱无法证明 1 万/10 万封的 SELECT、序号维护与搜索成本，应补充固定大邮箱数据集。
4. **用运行时堆栈定位分配与偶发长耗时。** 本轮显示落盘、MIME 和后台补建有偶发峰值，但阶段 API 无法指向具体热点方法和分配类型。下一轮按用户确认使用 **Release + Portable PDB、dotnet-trace 采集、PerfView 分析**，详见 [采集方案](dotnet-diagnostics.md)。正式吞吐测量与 trace 采集分开，减少采集干扰。
5. **重复配置读取与事务竞争。** `system_settings` 高频读取平均不足 1 ms，优先级低于大文本和 IMAP；可评估利用现有配置版本缓存空值和固定配置。串行化写事务发生过死锁并重试恢复，应继续统计竞争频率、锁持有时间和一致的锁顺序，保留配额、UID、持久化语义。
6. **补足真实外发和硬件容量比较。** 此轮主要覆盖入站 SMTP 和客户端收取，不能证明外发 Direct MX 的解析、DKIM、连接复用或多 MX 回退收益。32gb 配置档也不能替代真实 32 GB 机器。连接复用在完成独立外发/TLS 故障矩阵前保持关闭。

## 证据与回退

原始记录位于 `builds/performance/remote-efficiency-20260930/`。`before-pressure.jsonl` 包含早期重试，统计时只采用每个 phase 最后一次 `phase-start` 之后的记录，不能把早期未完成轮次混入有效比较。`after-32gb` 所有负载轮次已完成，收尾导出遇到服务重启中断，通过独立脚本恢复诊断导出；诊断窗口与逐轮负载统计分别报告。

最终代码完整回归 **422 项通过**，报告为 `remote-final-regression.trx`；包含此前 SQLite 和 MySQL 本地实际数据库专项验证。远端 Azure MySQL 本轮实际运行增量迁移、收信、检索补建和诊断读写。尚未在此服务器完成全部协议、真实 Direct MX/TLS 回退、1 万/10 万邮箱搜索与 100 IMAP IDLE 的端到端性能矩阵。

检索异常可关闭 `MessageSearch:Enabled` 并重启，检索表保留，搜索恢复原文检查。Direct MX 连接复用仍默认关闭，未将组件级 SMTP 复用测试解释为公网外发验收。本轮内存修复的收益不能替代最初计划中所有阶段的独立性能验收。
