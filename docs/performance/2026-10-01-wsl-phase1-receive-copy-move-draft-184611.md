# 第一阶段：收信事务与 COPY/MOVE（草稿）

## 实现范围

MySQL 写入首先按去重后的域 ID 顺序锁定域配额行，随后读取及更新账户和邮箱；SQLite 保留原写事务语义。协调器保留 Serializable 和有限冲突重试，未新增配额预留表、未降低隔离级别。入站收件人、规则与转发域在事务前形成计划，事务内复核版本和全部目标；目标变化触发回滚重建，禁止逆序临时追加锁。解析、冷规则加载和文件保存位于写事务外，提交成功后才发通知。

UID COPY/MOVE 把选择区间下推数据库；序号路径分页映射 ID/UID，执行时保持序号语义。选中数据分批 256 条，只有实际变更对象进入跟踪；多批仍在整条命令的一个事务里提交。保留 UID/ModSeq、跨账户归属、Trash、软删除及配额行为。

## 版本与问题修复

早期 phase1 独立产物与最后组合候选的配置及后续源码不同，不能把组合测量全部归因于锁协调器。大邮箱真实协议进一步发现 baseline 和 safe-final 的 STORE/EXPUNGE GUID 集合 SQL 映射问题；protocol-final 为此新增修复和实际 MySQL 回归，最终 STORE/EXPUNGE、IDLE 和 COPY/MOVE 验收必须使用新产物。基线克隆恢复若通过数据库维护完成，要单独记载，不能声称基线 STORE/EXPUNGE 协议成功。

## 已有与待完成验收

safe-final 实际 444 回归覆盖共享域并发配额、两账户 APPEND、COPY/MOVE、取消与回滚等。旧组合候选并发 4 的 1 MiB/10 MiB 收信 P95 改善 54.16%/22.49%，吞吐提高 20.68%/14.71%，但当时 Prepared=true，最终默认 Prepared=false 的 protocol-final 五轮对照已完成，1 MiB/10 MiB P95 改善 59.16%/51.42%，吞吐提高 44.78%/29.33%，每尺寸每版本 80/80 成功。

pending：1 万/10 万共享引用及不同正文中单封 UID、区间 COPY/MOVE 的每轮时间、SQL 返回/跟踪行数和内存；收信冲突重试规范化日志。必须分别统计重试事件、发生重试的邮件与最终失败，避免把派生回滚日志重复当失败。高并发 8/16 的 451 资源保护不能算作无限容量提高。

## 回退

锁协调与区间选择没有独立功能开关，回退使用已保存基线或前一个通过验收的产物及其匹配 PDB，再做健康和协议确认。数据库结构与既有数据保留；基线本身有已发现的 STORE/EXPUNGE 问题，因此发生该类问题时应优先保留修复产物，不能把已知错误基线当作安全通用回退。回退不清空配额账本、邮箱或审计数据。
