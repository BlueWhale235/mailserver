# 收敛协议审计以降低收信内存与数据库开销（2026-09-29）

## 改动

普通 SMTP 收信不再为了写审计记录二次读取、复制和解析整封 MIME 邮件，也不再查询重复内容与本地域名伪造情况、检查重复单值头部并写入协议审计。SMTP 认证与 `MAIL FROM` 的成功、失败也不再单独向审计表写库；原有身份验证、发件人授权、拒绝响应和运行日志仍执行。IMAP 协议层原本没有逐封审计写入，无需修改。

管理员 API 的操作审计保持原样。按用户选择，插件主动写入的审计及插件接口也保持原样。数据库结构和现有历史记录均不变。

## 原因与测量

旧入站路径会先解析邮件用于规则与投递，再为 MIME 审计重新打开邮件文件，复制到可增长的 `MemoryStream`，调用 `ToArray()` 生成第二份原文，最后再次解析 MIME。10 MiB 邮件并发时，这一过程会制造与邮件大小成比例的大对象分配。重复邮件和本地域名诊断还分别增加数据库读取；SMTP 认证及信封发件人操作原本另有审计写库。

本机 Release SQLite 基准（1 MiB、本地单收件人、预热一轮后测量五轮）在本次修改后得到：整体耗时中位数 14.21 ms、样本 P95 19.90 ms、分配量中位数 1,665,264 B、SQL 次数中位数 13、逻辑连接打开次数中位数 2。此前的[数据库阶段报告](../database-stage-optimization-2026-09-29.md)记录了 15,366,728 B 分配和 16 次 SQL；两次测量跨越其他代码改动和运行状态，不能将差额全部归因于本次修改，也不能据此推断线上吞吐提升。

## 验证与剩余限制

已验证普通收信与重复头邮件仍能落库，协议审计记录为空；已认证账号和别名的 `MAIL FROM` 仍获接受，未授权发件人仍被拒绝，且不产生协议审计。后端 Release 全量 401 项测试通过。

这次没有重新对约 887 MiB 的测试服务器做 10 MiB 持续并发压测，也没有在独立 MySQL 验收库复测，因此真实容量边界仍以[上次实测](2026-09-29-mysql-10m-capacity.md)为准。现有规则解析及 MIME 正文提取仍可能为大邮件分配大量内存；配置快照缓存本身有 LRU 和大小上限，1 GB 档缓存预算为 8 MiB，不能解释上次达到数百 MiB 的进程换页。下一步应在真实 10 MiB 并发下分别采集托管堆、原生内存和缓存占用，再决定是否需要限制正文解析或调整缓存策略。
