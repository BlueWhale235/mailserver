# MySQL 收信并发修复与复测报告（2026-09-29）

## 改动

SMTP 收信事务在 MySQL 死锁（错误码 1213）或锁等待超时（1205）后，会从新的数据库上下文重新读取规则、配额和邮箱状态，并在短暂随机退避后重试。最多尝试八次；全部失败时仍向客户端返回临时错误，不会把未提交的邮件报为成功。SQLite 路径不启用这项重试。

后台新增明确的 32 GB 资源档位。其缓存预算为 256 MiB、单项缓存上限 32 MiB、并行投递上限 64、SMTP 连接请求上限 512、IMAP 连接请求上限 1024。档位是配置预设，不会增加服务器物理内存。

## 环境与方法

- 测试服务器为 Ubuntu 24.04、Linux x64，物理内存约 887 MiB、交换空间 2 GiB；数据库为独立的 Azure MySQL 压测库。
- 最终部署版本为 `dac94dd`，二进制 SHA-256 为 `abc68bdb9da300e6eecbffc8e2b87466079f7fdbae292e209a29a3e9b2eae302`。
- 后台压测期间选用 32 GB 档；SMTP 单来源连接额度临时设为每分钟 10,000、突发 1,000、同时连接 256。配置文件中的 `Smtp:MaximumConnections=200` 仍限制实际 SMTP 总连接数为 200。
- 测试客户端与服务端在同一台服务器上，通过本机 25 端口投递到 `test@3023198.xyz`。每封邮件使用新的 SMTP 连接，未使用第三方邮箱账户发信。
- 每个并发场景做五轮，每轮发送十六封约 1 MiB 邮件；分别使用八和十六个并发连接。10 MiB 顺序场景先预热一封，再测量五封。总耗时包括连接、信封、DATA 和服务端确认。P95 按每轮成功样本的最近秩法计算。

| 场景 | 成功／尝试 | 五轮耗时中位数 | 五轮 P95 范围 | 观测到的峰值 RSS |
|---|---:|---:|---:|---:|
| 1 MiB、8 并发 | 80／80 | 约 0.34–1.07 秒 | 约 1.05–3.05 秒 | 344 MiB |
| 1 MiB、16 并发 | 80／80 | 约 0.65–10.00 秒 | 约 1.16–13.64 秒 | 437 MiB |
| 10 MiB、顺序发送 | 5／5 | 369 毫秒 | 1,179 毫秒 | 未连续采样；测试结束时 RSS 约 300 MiB |

十六并发首轮的延迟明显偏高，后续几轮下降。本次样本规模较小，且客户端与服务端同机，不能将这些数字外推为长期吞吐量。数据库核对显示该测试邮箱共有 251 封邮件及 251 个不同的 UID；其中还包含前期测量邮件，UID 没有重复。

作为故障定位对照，旧二进制在相同域名、已放宽连接额度的首轮八并发测试中仅有 6／16 成功；随后用户误操作移除了 1Panel 的服务托管项，剩余轮次无效。中间版本五轮八并发共 79／80 成功。最终版本五轮八并发和五轮十六并发均全部成功。由于这些阶段存在重启与负载变化，不能据此给出严格的吞吐提升倍数。

## 验证与剩余问题

- 部署后健康检查返回 HTTP 200，Supervisor 服务保持运行。
- 最终代码的 401 项自动化测试全部通过。
- 32 GB 档及临时连接额度在后台保存并由运行进程上报为已应用。压测结束后，两项设置已恢复到原来的 1 GB 档和默认 SMTP 单来源额度；运行进程重新上报为已应用。
- 收信重试消除了本次测试中的 SMTP 451，但并未消除 MySQL 死锁本身。十六并发的首轮尾部延迟仍高，下一步应分析事务持锁范围与锁顺序，而不是继续无限增加重试次数。

- 本次没有独立 MySQL 验收库，因此未运行要求单独验收库的专项套件；也未测量内存分配量或数据库连接池开关对照。
