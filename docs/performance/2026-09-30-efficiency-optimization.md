# 邮件服务器效率优化：实现与验收记录

## 基线与实现

实施开始时 HEAD 为 `cac55ff2e86adc9e808fea65143c17a085d6097b`。当时存在 14 个已修改文件、1 个已删除文件，以及两个 HTML 草稿和 Python 缓存；既有改动均保留。独立 `efficiency-baseline` 工作区以该提交为底，带入实施前的配置、资源管理、连接保护和相关测试改动，两个共享编辑文件恢复到优化前逻辑。两组使用同一基准代码；基线不是单纯的干净 HEAD。

本轮实现：队列状态合并聚合；邮箱未读数由数据库计算；外发直接使用可定位流，非可定位流落临时文件，单次尝试只解析、签名一次；Direct MX 的 MIME 内容可保持文件引用，DKIM 在兼容七位传输的准备后签名。IDLE 同邮箱订阅共享刷新，收信、APPEND、标记、EXPUNGE、COPY/MOVE 和重命名在提交后发本地提示；跨进程与其他维护写入由原轮询兜底。新外发任务及手动重试会唤醒本地 Worker。

新增 `message_search_records`，两种数据库都有增量迁移。检索每批最多 32 封，以原有规范化和子串语义匹配预解析数据；这是减少原文 I/O 和重复解析，仍需扫描邮箱，不是分词全文索引。记录不完整或不可用时核查原文，避免漏匹配。历史补建单并发、限批次、失败延迟重试，并遵守大型 MIME 处理许可。

Direct MX 连接复用有独立开关，默认关闭；最多四条空闲连接，每目标一条，30 秒空闲、5 分钟寿命、50 封限额。租用独占，复用前检查，异常或结果不明时销毁；中继和 STS testing 模式保持逐次连接。

## 正确性验收

专项用例覆盖空队列与各状态、标记大小写及边界、软删除、中文和重音搜索、缺失及截断记录回退、旧版本、关闭索引、UTF-8 文本预算和删除级联；100 个订阅者的首次读取及提交提示各只触发一组邮箱查询。连接测试通过本地 SMTP 服务器实际发送 20 封邮件并复用一条连接，另覆盖策略键隔离、消息限额、空闲过期及未确认尝试淘汰。DKIM 用例验证中文正文签名在七位发送准备与重新序列化后仍有效。

SQLite 的实际迁移和既有协议、配额、租约、SRS/DKIM 回归由完整测试套件执行，421 项通过；最后的 IDLE 和外发调整分别通过 85 项、28 项相关回归。另在 WSL 隔离运行 MySQL 8.4.11，实库验收 3 项通过，执行新迁移、配置版本竞争、多 Worker 租约、未读聚合、队列概览、中文与主题预解析搜索及软删除过滤。结果在 `builds/acceptance/efficiency-results/efficiency-mysql.trx`。

实库测试要求 `SKIP LOCKED` 竞争时不重复领取，并通过下一轮领取验证剩余任务不遗漏，不再假设每个竞争事务都能立即填满批次。保留原租约实现。标记匹配值使用参数及二进制排序规则，避免 MySQL 反斜杠字面量和重音不敏感排序差异；GUID 批量过滤使用有界等值参数，避免当前 MySQL EF 提供程序的集合映射缺陷。最后一次完整套件包含 MySQL 实库共 421 项通过；之后的标记排序调整由 SQLite/MySQL 专项 12 项回归验证，结果在 `efficiency-final-regression.trx` 和 `efficiency-final-database.trx`。

## Linux 持续测试

使用 WSL 中的独立 systemd 服务、独立 SQLite 数据库和回环端口；`MemoryMax=1G`、`MemorySwapMax=0`。测试交替使用 1/10 MiB 邮件以及 2/3 个同时请求，每轮间隔约 10 秒，持续 1800 秒；这是稳态可靠性测试，不是极限吞吐测试。仅测试账号的配额提高到 8 GiB 以容纳积累的测试数据，协议资源保护保持原设置。

入口为 `scripts/acceptance-efficiency-linux.sh <已发布的 Linux mailserver 路径>`，配套 `scripts/efficiency-sustained-traffic.py`。测试中 3 并发会触发现有活跃邮件限制，必须单独报告 451 限流，不可通过提高并发上限掩盖。测试记录 cgroup 内存、Swap、OOM 事件、健康检查和各轮延迟；cgroup 内存包括文件页缓存，应结合进程 RSS 解读。

1800.01 秒内完成 180 轮、成功收信 360 封，约 1.93 GiB；180 次健康检查全部正常。另有 90 次 SMTP DATA 失败，与日志中的 90 次活跃邮件限流一一对应。成功请求的整体 P95 为 513.88 ms；由于主动轮间等待，不能把接收速率解释为服务吞吐上限。358 次内存采样最大 1,073,586,176 B（包括文件页缓存），最后为 744,337,408 B；Swap 始终为零，OOM 和 OOM kill 均为零，内存上限回收事件 4857 次。约第 16 分钟的进程 RSS 观察为 479 MiB，历史最高约 595 MiB；该观察未落盘，不能作为最终进程峰值证明。

日志与采样在 `builds/acceptance/efficiency-endurance-20260930/`。运行中编辑入口脚本造成收尾解析错误，最终 systemd 峰值和进程状态未保存；退出清理仍停止了测试服务，以上结论来自已落盘的负载与内存采样。该次二进制保持固定；随后完善的通知覆盖、外发文件引用和可选 GC 日志不能冒充已在这次持续测试中运行。

修正后的脚本已用包含上述更新的二进制额外运行 30 秒：6 封接收成功、1 次明确标记为 451 限流、无其他错误，服务健康。收尾状态、进程 RSS、GC 日志均正常保存，峰值 cgroup 内存 444,829,696 B；记录在 `builds/acceptance/efficiency-final-smoke-20260930/`。之后 MySQL 实库发现的参数兼容修正由数据库和完整回归验证。短测仅验证脚本与启动行为，不替代最终版本的完整持续验收。

## 回退与剩余验收

按对应提供程序先应用增量迁移，再运行新版。检索异常可关闭 `MessageSearch:Enabled` 并重启；连接复用关闭 `SmtpConnectionReuse:Enabled` 并重启 Worker。保留检索表，避免回退时破坏已有检索数据。现有资源限流、数据库租约和轮询始终保留。

尚需在相同资源档位、同一数据规模与独立负载机上比较真实 SMTP/IMAP/TLS 和外发路径，并对最终版本完整复跑持续负载。当前查询基准、组件连接测试、MySQL 实库回归与持续收信结果不能替代全部端到端场景的五轮对照；尤其尚未实测完整外发路径的 10 MiB 峰值分配与不同 MX 能力回退、远端断连及 TLS 策略切换。连接复用因此保持默认关闭。
