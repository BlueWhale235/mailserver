# 10 MiB 邮件逐级加压与容量边界（2026-09-29）

## 结论

这台测试服务器在本次条件下能够接收 4 个同时发送的 10 MiB 邮件，但这不是可持续容量：该档位的吞吐量已从单并发的 13.4 MiB/s 降到 1.86 MiB/s，进程交换空间升至 648.7 MiB，P95 升至 24.6 秒。2 并发已开始明显换页，吞吐量也下降。因此，按“不明显换页、吞吐不倒退”的实用标准，本次测得的可接受档位是 **1 并发**；2 并发是第一个未达标档位。它是这台约 887 MiB 物理内存机器上的单次测试边界，尚不能当作长期稳定负载上限。

## 代码与环境

- 本轮将 MIME 检查和部分收信诊断移出 MySQL 投递事务，缩短事务持锁时间；新增回归测试验证 MIME 检查可在单独连接上写入数据库。版本 `0d64fa6` 的 402 项自动化测试通过。
- 部署 Linux x64 自包含二进制，SHA-256：`38c4b7e3dd7d32b174d12113c81088758d43403d2f8e2c93546e8ee7e0653f42`。测试后服务就绪检查返回 HTTP 200。
- 测试服务器为 Ubuntu 24.04，物理内存约 887 MiB，交换空间 2 GiB。后台临时选择 32 GB 资源档，临时放宽 SMTP 单来源连接额度；这只改变软件限制，不增加物理内存。应用层 SMTP 总连接上限仍是 200。
- 仅重置 Azure MySQL 的 `app-mailserver` 压测库并重新创建测试域 `3023198.xyz`、收件账号 `test@3023198.xyz`。重置前的 MySQL 邮件文件移至 `/www/mailserver-loadtest-archive-before-reset/messages`；原始 SQLite 数据仍在 `/www/mailserver-archive-20260929-pre-loadtest`，未改动。
- 客户端与服务端同机，通过本机 SMTP 25 端口发送。每封约 10 MiB，使用新连接和唯一 Message-ID。先预热一封，再按 1、2、4、8……并发逐级加压；每档至少四封，实际本次在 4 并发后因资源压力停止。耗时包含 SMTP 建连、信封、DATA 和确认。P95 使用最近秩法。资源以约 50 ms 间隔采样。

## 后续测法与限制

已增加可复用的 [逐级压测脚本](../../scripts/smtp-adaptive-pressure.py)。它在每档结束后检查投递失败、健康状态、P95、进程 Swap、可用内存和吞吐量回退；任一指标越界就停止并报告最后通过的档位。阈值和最大并发均可通过命令行调整，不能用软件配置的 32 GB 档代替实际资源采样。需要测网络和服务器的整体能力时，应从另一台客户端运行，并单独采集服务器资源。

本次每档样本少、客户端与服务端同机、Azure MySQL 经公网访问，且逐级测试会累积垃圾回收和换页影响；因此只能判定当前机器在此配置下的明显拐点，不能给出长期吞吐上限或严格的优化前后收益倍数。下一轮宜先消除 MIME 检查对大邮件的整封内存复制，再在恢复后的机器上重复多轮，比较并发 1 与 2 的持续负载及分配量。

压测后已恢复原有 1 GB 档及 SMTP 单来源额度（每分钟 120、突发 30、同时 16），重启服务释放测试造成的内存压力。数据库仍保留本次压测邮件以供排查。
